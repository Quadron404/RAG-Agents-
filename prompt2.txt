ABSOLUTE BROWSER REQUIREMENT — THE HEART OF THIS QA SYSTEM
======================================================================
The ONLY browser system permitted for every browser-based test in this file is the remote Browserless MCP server already configured in the AI7 agent environment:

AI7 → MCP → browserless → remote → https://mcp.browserless.io/mcp

Use that exact configured MCP server for all app navigation, browser interaction, DOM and accessibility inspection, screenshots, viewport/device emulation, keyboard/touch interaction, console inspection, network request/response inspection, downloads and end-to-end user journeys. The AI7 agent MUST invoke the configured browserless MCP tools; it is not enough to mention Browserless in a report.

PROHIBITED SUBSTITUTES:
- Do not use local Playwright, local Chrome/Chromium, a local browser, a local browser daemon, or a developer's personal browser.
- Do not use a different hosted browser provider.
- Do not use source-code inspection, static screenshots, curl, API-only tests or unit tests as a substitute for the real Browserless user journey.
- Do not use RAG Agents' own Computer/noVNC/CDP feature as the QA browser. That is a product feature under test, not the external Browserless test system.
- Do not claim a browser test passed if the Browserless MCP session was not actually used.

If Browserless cannot connect: retry the configured MCP connection, inspect the MCP tool error, diagnose configuration/network/authentication issues available inside AI7, and retry. If it remains unavailable, record a hard blocker with exact error, timestamp and attempted recovery. Continue source-level and unit tests that do not require a browser, but mark every browser-dependent scenario BLOCKED; never substitute another browser and never report it as passed.

COMPULSORY REPRODUCE → FIX → TEST → DEPLOY → RETEST LOOP
======================================================================
This loop is mandatory for EVERY defect and every incomplete feature:

1. REPRODUCE: Use Browserless against the deployed app. Record exact URL, account/test identity class (never credentials), viewport, steps, expected behavior, actual behavior and repeatability.
2. CAPTURE: Save before-fix screenshot(s), browser session/run identifier, console errors, failed network requests, response status and relevant DOM/accessibility evidence. Redact cookies, tokens, private content and secrets.
3. ROOT CAUSE: Trace the failure through the actual frontend component, state store, Worker route, D1 migration/query, backend/Codespace service or provider boundary. Identify the precise root cause; do not guess.
4. FIX: Implement a durable functional fix. Do not hide errors with CSS, fake success toasts, hardcoded sample data, optimistic state without reconciliation, weakened auth, skipped approvals or mock-only behavior.
5. REGRESSION: Add or update targeted unit, integration, migration, contract and security tests. Run all relevant tests, typechecks and production builds. Browserless is still compulsory for browser behavior.
6. DEPLOY: Deploy the actual changed frontend assets and Cloudflare Worker to the existing production Worker using the configured CLOUDFLARE_API_KEY environment secret. First inspect existing wrangler configuration and the installed Wrangler authentication contract. If that variable is not consumed directly by Wrangler, use a supported secure in-memory environment adapter; never echo, print, log, serialize, commit or ask the owner to paste the key. Do not invent new secrets. Apply migrations only when the code requires them and the migration is reviewed, backward-compatible and safe for existing user data.
7. RETEST PRODUCTION: Open the deployed production URL in the same Browserless MCP. Repeat the exact failing steps and test adjacent flows, refresh, second tab and responsive viewport where relevant. Capture after-fix evidence.
8. REPEAT: If any expected result still fails, return to root-cause analysis and repeat steps 3–7 until it works. Do not stop after one repair attempt.
9. CLOSE: Mark PASS only when the deployed production flow passes in Browserless and relevant regression tests pass. Otherwise record BLOCKED with a precise external dependency. A code commit, local test, screenshot or successful deploy alone is not a pass.

A QA prompt is not complete because the agent has written a report. It is complete only after the required scenarios have been exercised, defects fixed, deployed and retested. Never claim completion for inaccessible authenticated functionality.

DESIGN AND PRODUCT BAR
Build an original premium product, not a clone. User priorities, in order:
1. Exceptionally smooth, refined, premium Apple/iOS-quality UI/UX.
2. Correct end-to-end application logic.
3. UI state, controls and messaging must exactly match backend reality.

Use a restrained deep-maroon identity, precise typography, clear hierarchy, deliberate whitespace, polished interaction states, subtle glass/depth where useful, high-quality responsive layouts, accessible controls and low-cost motion. Avoid generic AI gradients, excessive cards, childish styling, clutter and fake activity. The Chief remains the singular visible assistant; specialists work behind Chief and surface only concise useful progress.

Claude Duet comparison principles verified from its official help material (https://support.claude.com/en/articles/17631495-get-started-with-claude-duet): one persistent main thread, separate topic channels sharing memory, text/voice interaction, connected-app work and confirmation before consequential actions. Use these product principles as competitive reference, not as permission to copy its proprietary visuals or exact interface. RAG Agents should add reliable desktop continuity, deeper computer/browser workflows, richer task provenance and strong cross-device behavior.

PROMPT 2: CHANNELS, SHARED MEMORY AND CONVERSATION LIFECYCLE
======================================================================
Test whether a true channel entity exists in the deployed product. Do not confuse a conversation list, a summary label or a localStorage grouping with channels. A channel must have durable owner-scoped identity and support its own name, optional description, icon/accent, ordering, archive state and conversations. Add server APIs for create, list, open, rename, metadata edit, pin/order, archive, restore, search and delete as supported. Ensure all queries enforce authenticated owner identity server-side; never trust a channel owner ID supplied by the model or browser.

In Browserless, create several channels for distinct synthetic topics, switch rapidly between them, start conversations, refresh, open a second tab and use a mobile viewport. Verify each channel's conversations and drafts stay correctly associated; no message may be routed to the previously active channel during rapid switching. Test archive/restore, ordering, search and deletion confirmation. Verify shared memory means relevant user-level context can be reused while channel-specific instructions and private content do not leak into unrelated channels. Prove ownership isolation with two safe test identities if available.

Acceptance: channel identity and membership survive refresh and cross-device use; existing conversations remain accessible; no cross-channel or cross-owner leakage occurs; every visible channel control works; destructive actions are explicit and recoverable where promised. Fix, deploy and retest.

- Use the exact AI7 Browserless MCP endpoint above for every browser test. Browserless outage means BLOCKED, not permission to switch tools.
- Maintain durable progress in the existing AI7_PROGRESS.md without erasing history. Do not create schedules or automations as part of QA.
- Do not repeat completed implementation work from prompt.txt. Use QA to find actual defects and verify the fix, not to create cosmetic churn.
- A release report must distinguish PASS, FAIL and BLOCKED. Never turn "source exists", "API returned 200", "build succeeded" or "deployed" into a claim that a real user journey works.
