PROMPT 1: Authentication, onboarding, and protected application shell

FEATURE DESCRIPTION AND TEST OBJECTIVE
RAG Agents is a Google-authenticated app. The Cloudflare Worker owns Google OIDC, D1 sessions, and the public frontend shell; Gmail consent is separate. Current live evidence: the root page is HTTP 200 and shows only “Continue with Google”; GET /auth/session returns authenticated:false; GET /auth/login returns HTTP 503 with “Google sign-in is not configured”. Source worker/src/index.ts returns this 503 when GOOGLE_CLIENT_ID or GOOGLE_CLIENT_SECRET is falsey, and worker/src/env.ts declares the secret. The direct Cloudflare Production settings query returned no secret bindings; recheck the exact service/environment and do not infer or invent secret values.

MANDATORY LIVE USER JOURNEY
Use a fresh Browserless context and inspect the visible sign-in shell, accessibility tree, links, page dimensions, console, failed requests, response headers, and protected routes. Follow the Google link only far enough to inspect the redirect/state flow. Inspect the actual Production secret/config state and source; do not conclude credentials are missing from authenticated:false. If an authorized AI7 test profile already exists, use it to test sign-in, reload, session persistence, settings, and logout. Never create or use a production bypass. Test denied OAuth, wrong account, expired state, and direct unauthenticated API/Computer/Files routes.

PASS CRITERIA
PASS requires the real configured sign-in route to work, a verified session to persist safely, protected routes to reject unauthenticated requests, logout to revoke access, and no test-bypass control to be exposed. If the Google secret is genuinely unavailable, mark only the credential-dependent journey BLOCKED with exact non-secret evidence; do not fabricate credentials or bypass auth, and continue all public-surface/security tests.

PROMPT 2: Persistent channels, shared memory, and one unified Chief chat

FEATURE DESCRIPTION AND TEST OBJECTIVE
Channels are first-class project workspaces, not merely separate conversations. Main is the user's persistent default. Each channel owns its conversations, channel memory, tasks, artifacts, and read state; permitted user-level memory may be shared across channels. Chief remains the only visible assistant identity. The previous source audit found a conversation-centric schema without channel_id; channel-summary tables alone do not prove a real channel model.

MANDATORY LIVE USER JOURNEY
In Browserless, sign in with the authorized test identity and inspect the channel-first navigation on desktop and mobile. Verify Main is created once, create at least two project channels, rename one, change metadata/order, pin, archive, restore, and switch rapidly. Send unique synthetic facts into each channel. Reload and open a second Browserless context for the same test identity; verify membership, active channel, ordering, read cursors, deep links, tasks, and history converge. Test that user-level preferences can cross channels only by policy and project-only facts never leak. Test back/forward, deleted/archived channel routes, and switching while a response streams.

PASS CRITERIA
PASS requires server-authoritative channel state, safe legacy conversation membership, one stable Main, one Chief identity, channel-scoped context, permitted shared memory, cross-device consistency, and no cross-channel leakage.

PASS CRITERIA
